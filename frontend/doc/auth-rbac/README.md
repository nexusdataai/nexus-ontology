## Architecture Overview

The UI never talks to AWS Cognito directly. All authentication goes through the backend API, which handles Cognito OAuth, token exchange, and session management. The frontend uses HTTP-only cookies for session state.

```
                  ┌──────────────────────────────┐
                  │       Browser (React SPA)     │
                  │                                │
                  │  backendAuthService.ts         │
                  │    credentials: 'include'      │
                  └───────────┬────────────────────┘
                              │
        ┌─────────────────────┼─────────────────────────┐
        │ EKS Mode            │ S3/CDN + ECS Mode        │
        │                     │                          │
        │ nginx proxy:        │ Direct cross-origin:     │
        │ /api/* -> backend   │ https://api.example.com  │
        │ (same origin)       │ (CORS required)          │
        └─────────┬───────────┼──────────┬───────────────┘
                  │           │          │
                  v           │          v
        ┌─────────────────┐   │  ┌────────────────────┐
        │ Backend (8000)  │   │  │  Backend (ECS/ALB)  │
        │ /api/v1/auth/*  │   │  │  /api/v1/auth/*     │
        │ /api/v1/rbac/*  │   │  │  /api/v1/rbac/*     │
        └────────┬────────┘   │  └────────┬────────────┘
                 │            │           │
                 v            │           v
        ┌─────────────────────────────────────────┐
        │            AWS Cognito User Pool         │
        │  Groups: Admin, Executive, SalesManager, │
        │          Rep                             │
        └─────────────────────────────────────────┘
```

## Deployment Modes

The UI supports two production deployment modes. The auth flow is identical; only the API routing differs.

### Mode 1: EKS (nginx proxy)

Frontend and backend both run in EKS. nginx serves static files and proxies API calls.

```
User -> ALB -> nginx (:8080)
                 |
                 ├── /           -> static React app
                 ├── /api/*      -> proxy to backend-svc-internal:8000
                 └── /auth/callback -> index.html (SPA route)
```

**config.json:**
```json
{ "api": { "baseUrl": "" } }
```

With `baseUrl: ""`, all API calls use relative URLs (`/api/v1/auth/login`), which nginx proxies. This means:
- No CORS required (same origin)
- HTTP-only cookies work natively (same domain)
- Backend is not publicly exposed (ClusterIP service)
- No mixed content issues

**nginx.conf** (relevant section):
```nginx
location /api/ {
    proxy_pass http://call-processing-prod-backend-svc-internal:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
}
```

### Mode 2: S3/CloudFront (CDN) + ECS Backend

Frontend is deployed as static files to S3 behind CloudFront. Backend runs on ECS behind an ALB with its own domain.

```
User -> CloudFront -> S3 Bucket (static files)
     -> ALB -> ECS Fargate (:8000) (API calls)
```

**Deployment flow:**
1. CloudFormation deploys S3 bucket + CloudFront distribution + WAF + SSL
2. CloudFormation deploys ECS cluster + ALB + SSL for backend
3. React app built and synced to S3 (`aws s3 sync dist/ s3://bucket/`)
4. `UIConfigGenerator` generates `config.json` with backend URL from CloudFormation outputs
5. `config.json` uploaded to S3, CloudFront cache invalidated

**config.json** (generated by deployer):
```json
{
  "api": { "baseUrl": "https://api.myapp.example.com" },
  "cognito": {
    "region": "ap-southeast-1",
    "userPoolId": "ap-southeast-1_xxx",
    "clientId": "abc123",
    "domain": "myapp-prod",
    "redirectSignIn": "https://app.myapp.example.com/auth/callback",
    "redirectSignOut": "https://app.myapp.example.com"
  }
}
```

Key differences from EKS mode:
- `baseUrl` points to the backend ALB URL (cross-origin)
- Backend must configure CORS (FastAPI middleware) to allow the CloudFront domain
- Cookies need `SameSite=None; Secure` for cross-origin requests
- Cognito callback URLs must include the CloudFront domain
- CloudFront uses Lambda@Edge for runtime configuration
- WAF protects the CloudFront distribution

### Comparison

| Aspect | EKS (nginx) | S3/CDN + ECS |
|--------|-------------|-------------|
| API routing | nginx proxy (same origin) | Cross-origin to ALB |
| CORS | Not needed | Required on backend |
| Cookies | Same-domain (Lax) | Cross-origin (None + Secure) |
| config.json | Static, `baseUrl: ""` | Generated from CloudFormation outputs |
| Backend exposure | Internal ClusterIP | Public ALB with SSL |
| CDN caching | None (nginx serves directly) | CloudFront with S3 origin |
| WAF | Optional (ALB-level) | CloudFront WAF |
| SSL | ALB terminates | Both CloudFront and ALB terminate |

### Local Development

**With backend:** Set `baseUrl` to `http://localhost:8000` in `public/config.json`.

**Without backend:** Enable auth bypass (see [Auth Bypass](#auth-bypass-development)).

## Authentication Flows

### Flow 1: Direct Cognito Login (Email/Password)

The primary login method. User stays in the app the entire time.

```
Login.tsx -> EnterpriseLoginForm (defaultTab="cognito")
  |
  | User enters email + password, clicks "Sign In"
  v
EnterpriseAuthContext.signInWithCognito(email, password)
  |
  v
backendAuthService.login(email, password)
  -> POST /api/v1/auth/login { email, password }
     credentials: 'include'
  |
  ├── Success: { user: { sub, email, groups, role, permissions }, session: { tokens } }
  |   -> Build EnterpriseProfile from response
  |   -> Store tokens in sessionStorage
  |   -> Backend sets nexus_session HTTP-only cookie
  |   -> navigate('/') -> Dashboard
  |
  └── Password change required: { requires_password_change: true, session: "..." }
      -> Show PasswordChangeForm
      -> POST /api/v1/auth/login/new-password { email, new_password, session }
      -> navigate('/') -> Dashboard
```

### Flow 2: ADFS SSO (Corporate Single Sign-On)

Browser redirects away from the app and comes back via OAuth callback.

```
EnterpriseLoginForm -> "Sign in with Corporate SSO"
  |
  v
backendAuthService.getADFSLoginUrl()
  -> Returns: /api/v1/auth/sso/adfs
  -> window.location.href = URL (full page redirect)
  |
  v
Backend -> Cognito (identity_provider=ADFS) -> ADFS login page
  -> User authenticates with corporate credentials
  -> ADFS -> Cognito -> /auth/callback?code=xxx&state=yyy
  |
  v
AuthCallback.tsx
  -> Extracts code and state from URL
  -> window.__completeOAuthCallback(code, state)
  -> POST /api/v1/auth/login/callback?code=xxx&state=yyy
  -> Backend exchanges code for tokens, creates session
  -> navigate('/') -> Dashboard
```

### Flow 3: Logout

```
signOutUser()
  -> POST /api/v1/auth/logout (credentials: 'include')
  -> Backend clears session, returns { logout_url? }
  -> backendAuthService.clearTokens() (clears sessionStorage)
  -> Context clears: user=null, profile=null, session=null
  -> If logout_url: window.location.href = logout_url
  -> Else: navigate('/login')
```

### Flow 4: Session Restoration (Page Reload)

```
EnterpriseAuthProvider mounts
  -> GET /api/v1/auth/me (credentials: 'include')
  |
  ├── 200: User profile returned -> restore context state
  └── 401: No valid session -> ProtectedRoute redirects to /login
```

## Auth Service API Calls

All calls from `backendAuthService.ts` use `credentials: 'include'` to send/receive cookies.

| Method | Endpoint | When Called |
|--------|----------|------------|
| `login(email, password)` | `POST /api/v1/auth/login` | User submits login form |
| `completeNewPassword(email, pw, session)` | `POST /api/v1/auth/login/new-password` | First-time password change |
| `initOAuthLogin()` | `GET /api/v1/auth/login/init` | OAuth flow init (returns authorization URL) |
| `loginCallback(code, state)` | `POST /api/v1/auth/login/callback` | OAuth redirect callback |
| `getADFSLoginUrl()` | Returns `/api/v1/auth/sso/adfs` | ADFS SSO (browser redirect) |
| `getCurrentUser()` | `GET /api/v1/auth/me` | Session check on mount and reload |
| `refreshToken(token)` | `POST /api/v1/auth/refresh` | Token refresh |
| `logout()` | `POST /api/v1/auth/logout` | User signs out |
| `changePassword(old, new)` | `POST /api/v1/auth/password/change` | Password change (backend returns 501) |

## Session and Token Management

### HTTP-Only Cookie (Primary)

The backend sets `nexus_session` after login:

| Attribute | Value |
|-----------|-------|
| HttpOnly | `true` (not accessible to JavaScript) |
| Secure | `true` (HTTPS only) |
| SameSite | `Lax` (EKS same-origin) or `None` (S3/CDN cross-origin) |
| Max-Age | `43200` (12 hours) |

The frontend never reads this cookie. It's sent automatically by the browser with `credentials: 'include'`.

### sessionStorage Tokens (Secondary)

After login, tokens are also stored in sessionStorage:
- `nexus_access_token`
- `nexus_id_token`
- `nexus_refresh_token`

These are cleared on logout and lost when the browser tab closes.

## Route Protection

### ProtectedRoute

```tsx
// App.tsx
const ProtectedRoute = ({ children }) => {
  const { user, loading } = useEnterpriseAuth();
  if (loading) return <div>Loading...</div>;
  if (!user) return <Navigate to="/login" replace />;
  return <>{children}</>;
};
```

### Route Map

| Route | Protection | Role Behavior |
|-------|-----------|---------------|
| `/login` | Public | Redirects to `/` if already logged in |
| `/signup` | Public | |
| `/auth/callback` | Public | Handles OAuth redirect |
| `/` | Protected + RepRedirect | Reps redirected to `/individual-dashboard` |
| `/settings` | Protected | Tabs filtered by permission |
| `/individual-dashboard` | Protected | All roles |
| `/my-calls` | Protected | All roles |
| `/webex/callback` | Protected | All roles |

## Roles and Permissions

### Roles

| Role | Level | Description |
|------|-------|-------------|
| `Admin` | 0 (Highest) | Full system access. `hasPermission()` always returns `true`. |
| `Executive` | 1 | Organization-wide dashboards, all calls, user management, compliance |
| `SalesManager` | 2 | Team dashboards, team calls, team management, compliance |
| `Rep` | 3 (Lowest) | Individual dashboard, own calls only, basic AI tools |

### Permission Enum

Defined in `src/types/auth.ts`:

| Permission | Category | Admin | Executive | SalesManager | Rep |
|------------|----------|:-----:|:---------:|:------------:|:---:|
| `VIEW_EXECUTIVE_DASHBOARD` | Dashboard | Y | Y | | |
| `VIEW_TEAM_DASHBOARD` | Dashboard | Y | Y | Y | |
| `VIEW_INDIVIDUAL_DASHBOARD` | Dashboard | Y | Y | Y | Y |
| `VIEW_ALL_CALLS` | Call Analysis | Y | Y | | |
| `VIEW_TEAM_CALLS` | Call Analysis | Y | | Y | |
| `VIEW_OWN_CALLS` | Call Analysis | Y | | Y | Y |
| `EXPORT_ALL_DATA` | Data Export | Y | Y | | |
| `EXPORT_TEAM_DATA` | Data Export | Y | | Y | |
| `EXPORT_OWN_DATA` | Data Export | Y | | | Y |
| `MANAGE_USERS` | Admin | Y | Y | | |
| `MANAGE_TEAM` | Admin | Y | | Y | |
| `MANAGE_SYSTEM` | Admin | Y | | | |
| `INVITE_USERS` | Admin | Y | | | |
| `VIEW_COMPLIANCE` | Admin | Y | Y | Y | |
| `ACCESS_AI_TOOLS` | AI/Analytics | Y | Y | Y | Y |
| `ACCESS_ANALYSIS_TOOLS` | Tools | Y | Y | Y | |
| `ACCESS_ENHANCEMENT_TOOLS` | Tools | Y | Y | Y | |
| `ACCESS_INTEGRATION_TOOLS` | Tools | Y | Y | | |
| `ACCESS_KNOWLEDGE_BASE` | Tools | Y | Y | Y | Y |

### How Permissions Are Assigned

```
1. User logs in -> backend reads Cognito group membership
2. Cognito group name = Role name (Admin, Executive, SalesManager, Rep)
3. Backend looks up permissions for role:
   - From RBAC config in DynamoDB (if available)
   - Or from DEFAULT_RBAC_CONFIG in rbac_model.py
4. Backend returns { role, permissions: [...] } in login response
5. Frontend stores in EnterpriseProfile.permissions
6. hasPermission() checks this array (Admin bypasses check)
```

### Frontend vs Backend Permission Differences

| Permission | Frontend (`auth.ts`) | Backend (`rbac_model.py`) |
|------------|---------------------|--------------------------|
| `INVITE_USERS` | Defined (Admin) | Not defined |
| `MANAGE_RBAC` | Not defined | Defined (Admin) |

The backend RBAC config is authoritative. The frontend `ROLE_PERMISSIONS` map is a static fallback used when the backend is unreachable.

## Permission Checking in Components

### hasPermission()

Provided by `EnterpriseAuthContext`:

```tsx
const { hasPermission } = useEnterpriseAuth();

// Admin always returns true (hardcoded shortcut)
// Others check profile.permissions array

// Conditional rendering
{hasPermission(Permission.VIEW_ALL_CALLS) && <AllCallsTable />}
{hasPermission(Permission.MANAGE_USERS) && <UserManagement />}
{hasPermission(Permission.EXPORT_ALL_DATA) && <ExportButton />}
```

### Data Scoping Example

The calls page uses permissions to determine data scope:

```tsx
if (hasPermission(Permission.VIEW_ALL_CALLS)) {
  // Show all organization calls
} else if (hasPermission(Permission.VIEW_TEAM_CALLS)) {
  // Show team calls only
} else if (hasPermission(Permission.VIEW_OWN_CALLS)) {
  // Show own calls only
}
```

The backend enforces the same logic server-side using `session_middleware.has_permission()`.

### Role-Based Route Behavior

```tsx
// RepRedirectWrapper in App.tsx
if (profile?.role === 'Rep') {
  return <Navigate to="/individual-dashboard" replace />;
}
// Executives and SalesManagers see the executive dashboard
```

Located in the Settings page. Requires `manage_rbac` permission (Admin only).

```
│  View All Calls            │  ●   │     ●     │             │     │
│  View Team Calls           │  ●   │           │      ●      │     │
│  View Own Calls            │  ●   │           │      ●      │  ●  │
│ ... more categories ...                                            │
└────────────────────────────┴──────┴───────────┴─────────────┴─────┘
```

Each permission row shows:
- Display name and description
- Risk level badge (low/medium/high/critical)
- Data scope badge (individual/team/organization)

**Edit mode:** Admin clicks "Edit" to enable toggles. Changes are optimistic (instant in UI). On save, calls `PUT /api/v1/rbac/roles/{roleId}/permissions` for each modified role. Rolls back on error.

#### Roles Tab

Lists all 4 roles with:
- Display name and description
- Hierarchy level
- Color-coded badge

#### Audit Log Tab

Shows history of RBAC changes:
- Timestamp, action, who made the change
- Previous and new permission sets
- Config version at time of change

Calls `GET /api/v1/rbac/audit?limit=50`. Only visible to Admin and Executive roles.

### useRBAC Hook

**File:** `src/hooks/useRBAC.ts`

```tsx
const {
  rbacData,                  // Full config: roles, permissions, categories, rolePermissions, auditLog
  loading,                   // Loading state
  saving,                    // Save in progress
  fetchRBACData,             // Refresh from backend
  updateRolePermissions,     // Save role's permissions (PUT to backend)
  toggleRolePermission,      // Toggle single permission for a role
  hasRolePermission,         // Check if role has a permission
  getPermissionsByCategory,  // Filter permissions by category ID
  getRoleById,               // Lookup role by ID
  getPermissionById,         // Lookup permission by ID
  getAuditLog,               // Fetch audit entries from backend
} = useRBAC();
```

**Data loading flow:**
1. Tries `GET /api/v1/rbac/config` (with `credentials: 'include'`)
2. Falls back to local `/results/rbac.json` if backend unavailable
3. Returns `{ status: "success", data: RBACConfig }` on success

## RBAC API Calls

All calls use `credentials: 'include'`.

### Load Full Config

```
GET {baseUrl}/api/v1/rbac/config
```

Called by `useRBAC` on mount. Returns roles, permissions, categories, rolePermissions map, audit log, and metadata.

### Update Role Permissions (Admin Only)

```
PUT {baseUrl}/api/v1/rbac/roles/{roleId}/permissions
Content-Type: application/json
Body: { "permissions": ["view_team_dashboard", "view_team_calls", ...] }
```

Returns 403 if caller is not Admin. Creates an audit log entry.

### Get Audit Log (Admin/Executive Only)

```
GET {baseUrl}/api/v1/rbac/audit?limit=50
```

Returns most recent RBAC changes.

### Check Permission (Utility)

```
POST {baseUrl}/api/v1/rbac/check?role=SalesManager&permission=view_all_calls
```

Returns `{ hasPermission: true/false }`.

### Get Role Permissions

```
GET {baseUrl}/api/v1/rbac/roles/{roleId}/permissions
```

Returns the permission IDs assigned to the role.

### List Permissions by Category

```
GET {baseUrl}/api/v1/rbac/permissions?category=call_analysis
```

## User Invitation (Placeholder)

The UI has components and services for user invitation, but these are **placeholder implementations**. The backend does not yet have user management endpoints.

**Component:** `src/components/settings/UserInviteManager.tsx`
- Form: email + role selection
- Table: pending invitations with resend/revoke actions
- Shows generated temporary password after invite
- Requires `INVITE_USERS` permission (Admin only)

**Service:** `src/services/userInviteService.ts`
- `inviteUser(email, role)` - Returns mock data
- `getUserInvitations()` - Returns mock data
- `resendInvitation(id)` - Placeholder
- `revokeInvitation(id)` - Placeholder

**To make functional**, the backend needs these Cognito admin endpoints:
- `POST /api/users/invite` -> `AdminCreateUser` + `AdminAddUserToGroup`
- `GET /api/users/invitations` -> List users with `FORCE_CHANGE_PASSWORD` status
- `POST /api/users/invitations/:id/resend` -> `AdminSetUserPassword`
- `DELETE /api/users/:id` -> `AdminDeleteUser`

Currently, users are created via AWS Console or CLI (see backend auth-rbac docs for commands).

## Auth Bypass (Development)

For local development without a running backend.

### Enable

**config.json:**
```json
{ "bypassAuth": true }
```

**Environment variable:**
```bash
VITE_BYPASS_AUTH=true npm run dev
```

### Behavior

When enabled, `EnterpriseAuthProvider` creates a mock Admin user:
- Email: `dev@local.test`
- Role: `Admin`
- All permissions enabled
- No backend calls made

All `hasPermission()` checks return `true`. All `ProtectedRoute` checks pass.
